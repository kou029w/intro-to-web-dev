# Day2

> **Note**\
> このページは2026年12月の研修に向けて編集中です。内容は変更されることがあります。

Day2では、USBでつないだM5Stack Core2（以下、Core2）をブラウザから操作します。
センサーの揺れを判定してサーボモーターで警告し、音声で計測間隔を変更し、自然言語で状態を問い合わせるところまで進めます。
Prompt APIとFile System Access APIは、[Day1](day1.md)で扱った内容を前提にします。

## 受講前の準備

Day1と同じPCで、[環境の確認](prompt-api/setup.md)のPrompt APIが動くことを確かめておきます。
Core2のUSBシリアル変換チップ用のドライバー（CP210xまたはCH9102）も、[M5Stack Core2の準備](hardware/m5stack-setup.md#uiflow2を書き込む)の手順1に従ってインストールしておきます。
会社のPCでは管理者権限が必要な場合があるので、当日までに済ませてください。
Core2は、UIFlow2とブリッジを書き込んだ状態で配布します。
当日は、[M5Stack Core2の準備](hardware/m5stack-setup.md#サーボモーターを配線する)のうち配線と接続の確認から始めます。
ポートが見つからない、サーボモーターが動かないなど、当日に起きやすい症状の対処は[困ったときは](troubleshooting.md)にまとめています。

## 連携例で確認すること

連携例の45分は、接続と設定に5分、揺れへの警告に10分、計測間隔の変更に10分、状態への質問に10分、保存と再読み込みに10分を割り当てます。
音声認識を利用できない場合は、同じ入力を文字で送信します。

モデルの出力、ブラウザが送ったコマンド、Core2の応答を照合してください。
「計測間隔を500ミリ秒にして」と指示したときは、モデルが返した値だけで完了とせず、Core2が返した間隔も確認します。

## コラム：小さく作って動かして確かめる開発の進め方

実際の開発は、どのように進めているのでしょうか。
ソフトウェア開発は不確実で、作業の見積もりも、利用者が本当に求めるものも、始める前には読み切れません。
今日の演習でも、サーボモーターがどこまで回るかや、モデルがどの値を返すかは、動かすまで分かりませんでした。
そこで、小さく作り、動かし、結果を確かめてから次に作るものを決める、という反復を繰り返します。

この進め方の背景にある考え方が、**アジャイル**です。
アジャイルは、変化に対応する機会を開発の中に頻繁に取り入れる考え方を指します。
特定の会議や手順を行えばアジャイルになる、というものではありません。
最初に取り組む実践は、品質の確保です。
動かしたものが壊れていれば、その結果から次の一歩を判断できないからです。

グループワークでも、最初から全部を作ろうとせず、1つの動作が意図どおりに動くことを確かめてから次に進んでください。
考え方の詳細は、講師のスライド[アジャイル開発概論](https://kou029w.github.io/intro-to-agile/)にあります。

## 研修の終わりに

この2日間で、言語モデルはブラウザの中でも動き、業務の文章や機器の操作にまで使えることを確かめました。
モデルから出力を得ること自体は、もう難しくありません。
価値が生まれるのは、その出力が正しいかを見極めるところです。
ミニチャレンジでは要約に含まれる数値を元の文章と照らし合わせ、連携例ではモデルが返した計測間隔をCore2の応答と照合しました。

見極めるには、何が正しいかを知っている必要があります。
業務の文章のどこに誤りが混ざりやすいか、センサーがどんな値を返したら異常なのかを知っているのは、現場で手を動かしてきた人です。

AIの広がりはいま佳境にあり、これまで経験を積む場になっていた作業も、モデルに任せられるようになりつつあります。
経験を積む場は、待っていても用意されないので、自分でつくるしかありません。
この2日間で動かしたサンプルは、その場をつくる出発点に使えます。
