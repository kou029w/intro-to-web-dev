# ミニチャレンジ：業務の文章を処理する小さなアプリ

> **Note**\
> このページは2026年12月の研修に向けて編集中です。内容は変更されることがあります。

Day1の午後は、70分で自分の業務の文章を処理する小さなアプリを作り、続く40分で成果を共有します。
ゼロから書き始めず、[Prompt APIサンプル集](prompt-api-demos.md)から近いサンプルを選んで改造します。
モデルの出力は[構造化出力](prompt-api.md#構造化出力で判断結果を得る)でJSONにして、プログラムで確かめられる形にします。
読みやすい要約にも元の文章にない数値が混ざることがあり、読み流すだけでは見落としやすいからです。

## 題材の探し方

何を作ればよいか分からず手が止まったら、新しい機能を考えるより、毎週のように繰り返している作業を思い出します。
問い合わせを読んで担当部署を決める、試験記録を読んで所見を1文にまとめる、不具合報告を重大度で分類する、といった作業です。
どれも入力する文章と、返してほしい形がはっきりしています。
題材を決めたら、自分で処理した結果を3件ほど用意しておきます。
この3件とモデルの出力を比べることが、成果の共有で説明する確かめ方になります。

## お題の例

次の5つは、どれもサンプルのプロンプトとスキーマを変えれば作れます。
各お題の「返させる形」は、JSON Schemaの`properties`の中身だけを示しています。
使うときは、次のように`type`と`properties`で囲み、`required`に必ず返させる名前を並べます。

```json
{
  "type": "object",
  "properties": { "summary": { "type": "string" } },
  "required": ["summary"]
}
```

プレイグラウンドを出発点にする場合、システムプロンプトとJSON Schemaは画面の入力欄で試せます。
コードで確かめる処理は、プレイグラウンドの`script.js`の`for await`ループの後に、`JSON.parse(outputEl.textContent)`の結果を調べる形で追加します。

### 試験記録の所見を1文に要約する

- 題材：耐久試験や校正の記録を読み、所見を1文にまとめる
- 出発点：[Prompt API プレイグラウンド](prompt-api-demos.md#prompt-api-プレイグラウンド)
- 返させる形：`"summary": { "type": "string" }`
- コードで確かめること：要約に含まれる数値が、元の記録にすべて出てくるか（`summary.match(/\d+(\.\d+)?/g)`で取り出して比べる）

### 不具合報告を重大度で分類する

- 題材：不具合報告や品質記録を、重大度と理由に分ける
- 出発点：[Prompt API プレイグラウンド](prompt-api-demos.md#prompt-api-プレイグラウンド)
- 返させる形：`"severity": { "type": "string", "enum": ["重大", "中", "軽微"] }, "reason": { "type": "string" }`
- コードで確かめること：`severity`が列挙した3つ以外の値にならないか、手作業で分類した3件と一致するか

### 問い合わせを担当部署に振り分ける

- 題材：製品の問い合わせを読み、担当部署を決める
- 出発点：[類義語検索](prompt-api-demos.md#類義語検索)
- 改造する箇所：`initialPrompts`に並べた入力例と回答例を、問い合わせと部署名のJSONの組に置き換えます。
  `promptStreaming()`に渡す文を問い合わせ本文に変え、第2引数に`{ responseConstraint: schema }`を渡します。
  `schema`はこのサンプルにないので、`const schema = { ... };`で定義します。
  出力は`resultEl`に入るので、確かめる処理では`JSON.parse(resultEl.textContent)`を調べます。
- 返させる形：`"department": { "type": "string", "enum": ["修理", "使い方", "出荷", "その他"] }`
- コードで確かめること：「その他」に入った件数（多ければ、選択肢か入力例が足りていない）

### 記録から日付と数値を抜き出す

- 題材：試験ログや点検記録から、日付、測定値、単位を一覧にする
- 出発点：[Prompt API プレイグラウンド](prompt-api-demos.md#prompt-api-プレイグラウンド)
- 返させる形：`"items": { "type": "array", "items": { "type": "object", "properties": { "date": { "type": "string" }, "value": { "type": "number" }, "unit": { "type": "string", "enum": ["℃", "%", "mmHg", "bpm"] } } } }`
- コードで確かめること：`date`が`/^\d{4}-\d{2}-\d{2}$/`に一致するか、`value`が元の文章に出てくる数値か

### 口頭の報告を書き言葉に言い換える

- 題材：作業報告の書き起こしや音声メモを、報告書に貼れる文に整える
- 出発点：[書き起こしのフィラー除去](prompt-api-demos.md#書き起こしのフィラー除去)
- 改造する箇所：`cleanFillers()`のシステムプロンプトを、丁寧語の報告文に言い換える指示に変えます。
  続く`session.prompt()`の指示文とスキーマは、取り除いたフィラーの配列の代わりに、言い換えた語句の組を返す形にします。
  その下の`const { removedFillers } = JSON.parse(result);`と表示の処理も、新しい名前`replaced`に合わせて書き換えます。
  書き換えないと`removedFillers`が`undefined`になり、`.length`を読むところでエラーになります。
- 返させる形：`"replaced": { "type": "array", "items": { "type": "object", "properties": { "before": { "type": "string" }, "after": { "type": "string" } } } }`
- コードで確かめること：言い換えの前後で、数値や型番が変わっていないか（両方から取り出して比べる）

録音しなくても、書き起こしの欄に文章を貼り付けて「フィラーを除去する」を押せば試せます。

## 進め方

70分の目安は次のとおりです。

1. 題材を選び、手作業で処理した結果を3件用意する（10分）
2. 出発点のサンプルをLiveCodesかStackBlitzで開き、そのまま動かす（10分）
3. プロンプトとスキーマを題材に合わせて変える（30分）
4. 用意した3件でモデルの出力と手作業の結果を比べ、コードで確かめる処理を足す（20分）

記録を残したい場合は、[OPFSへの保存と読み込み](file-system.md#opfsへの保存と読み込み)の実行ブロックのコードを組み込みます。
LiveCodesやStackBlitzの画面ではファイル選択画面を開けないため、そこで改造する場合はOPFSに保存します。

## 業務の文章を入力するときの注意

Prompt APIに渡した入力は端末の外に送られません。
ただし、気象データのサンプルのように外部のAPIを呼ぶサンプルを改造する場合、そのAPIに渡した値は通信先に送られます。
社外秘を含む文章を使う場合は、社内規程に従って扱います。

## 成果の共有

40分の成果の共有では、1人2分程度で次の2点を説明します。

- 何を入力し、モデルに何を返させたか
- モデルの出力が正しいかを、どう確かめたか
